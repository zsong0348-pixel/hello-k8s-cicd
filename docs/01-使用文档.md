# hello-k8s-cicd 使用文档

适用范围：Windows + PowerShell + Docker Desktop 的本地学习环境。下面的 GitHub 仓库和 GHCR 镜像属于 `zsong0348-pixel`；发布步骤要求你有该仓库 `main` 分支的写权限。只想体验运行中的应用，不需要 GitHub 写权限，也不需要每天登录 Argo CD。

## 1. 先弄清发布链路

```text
修改 app.py -> 推送 main -> GitHub Actions 测试并推送 GHCR 镜像
-> Actions 提交 k8s/deployment.yaml -> Argo CD 同步 Git -> Kubernetes 更新 Pod
```

Argo CD 是这条链路的部署执行者。首次搭建必须安装 Argo CD 并注册本项目；日常发布只需在 GitHub Actions 成功后查看它是否 `Synced / Healthy`。详见 [03-Argo CD 使用文档](03-ArgoCD使用文档.md)。正常发布不要手工 `kubectl apply -f k8s/`。

## 2. 第一次使用：准备环境

已有可运行的 Docker Desktop、Argo CD 和 `hello-k8s` Application 时，直接到第 3 节。

1. 安装并启动 Docker Desktop，在设置中启用 Kubernetes，等待 Docker Engine 运行且 Kubernetes 就绪。安装 PowerShell、Git、`kubectl`；在 PowerShell 中分别运行 `docker version`、`git --version`、`kubectl version --client` 确认命令可用。
2. 打开普通 PowerShell，选择本地集群，确认节点为 `Ready`：

   ```powershell
   kubectl config use-context docker-desktop
   kubectl get nodes
   ```

   先看当前 context 再执行后续命令：下面的安装和部署命令都会作用到它指向的集群。
3. 把项目克隆到自己选的目录，然后进入项目根目录；已有本地仓库时只执行 `cd`：

   ```powershell
   git clone https://github.com/zsong0348-pixel/hello-k8s-cicd.git
   cd .\hello-k8s-cicd
   git remote -v
   ```

   `git remote -v` 应指向上面的 GitHub 仓库。不要照搬别人电脑上的绝对路径。
4. 按 [03-Argo CD 使用文档](03-ArgoCD使用文档.md) 第 1 至 3 节安装 Argo CD、注册 `argocd-application.yaml` 并检查同步。这里不能只安装 Argo CD：还必须创建名为 `hello-k8s` 的 Application，Argo CD 才知道要部署哪个仓库。
5. 首次部署后确认 GitHub 的 `hello-k8s` Package 对外可读，否则 Pod 会显示 `ImagePullBackOff`。操作位置及检查方法见 [02-GitHub配置详解](02-GitHub配置详解.md) 第 5 节。仓库公开不代表镜像包也公开。

## 3. 每次启动后检查

打开 Docker Desktop，等待 Engine 和 Kubernetes 就绪。在 PowerShell 中执行：

```powershell
kubectl config use-context docker-desktop
kubectl get nodes
kubectl -n argocd get application hello-k8s
kubectl -n hello get deployment,pods,service
```

预期：节点 `Ready`；Application 为 `Synced / Healthy`；Deployment `2/2`；两个 Pod 为 `1/1 Running`。刚启动或刚发布时可以暂时是 `Progressing`，等待数分钟并重新检查。没有 `argocd` 命名空间或 Application，回第 2 节完成首次安装。状态长期异常，按第 8 节及 Argo 文档排查。

## 4. 浏览器访问应用

在一个 PowerShell 窗口运行：

```powershell
kubectl -n hello port-forward svc/hello-k8s 8081:80
```

看到 `Forwarding from 127.0.0.1:8081 -> 8080` 后保持该窗口打开。在浏览器访问 `http://localhost:8081/`，预期 JSON 中 `message` 为 `hello from Kubernetes`，`version` 是镜像对应的 Git SHA。再访问 `http://localhost:8081/healthz`，预期 `{"status":"ok"}`。也可以在另一个 PowerShell 中执行：

```powershell
Invoke-RestMethod http://localhost:8081/
Invoke-RestMethod http://localhost:8081/healthz
```

关闭转发窗口或按 `Ctrl+C` 后，浏览器地址不再可用。若提示 8081 被占用，先关闭旧的转发窗口；找不到时改用 `kubectl -n hello port-forward svc/hello-k8s 18081:80`，并访问 `http://localhost:18081/`。端口被占用不代表旧转发仍可用。

## 5. 发布一个新版本

前提：有该仓库 `main` 写权限，GitHub Actions 已启用且具有仓库写入权限，GHCR 镜像包可供集群拉取。配置位置见 [02-GitHub配置详解](02-GitHub配置详解.md) 第 1、5 节。团队启用分支保护时，按团队的 PR 流程操作；当前流水线还要求机器人能推送 `main` 中的 `k8s/deployment.yaml`。

### 第 1 步：确认仓库和工作区

在项目根目录执行：

```powershell
git branch --show-current
git status -sb
git fetch origin main
git status -sb
```

以下示例以 `main` 为当前分支。`git status` 若显示已有修改或暂存文件，先确认哪些是你的工作，不要用 `git add .` 顺手提交无关文件。若显示 `behind`，在工作区干净时运行 `git pull --ff-only origin main`。若显示 `ahead ... behind ...`，本地与远端已经分叉，`--ff-only` 会失败；先停下发布，确认本地提交和远端提交的来源，再由仓库维护者决定如何合并或变基，不要用强制推送覆盖远端。Actions 的机器人提交会让远端多出一次部署版本提交，所以每次发布前都要重新拉取。

### 第 2 步：修改并本地检查

打开 `app.py`，把首页返回的 `"hello from Kubernetes."` 改成 `"hello from version 2"` 并保存。检查：

```powershell
git diff -- app.py
docker build -t hello-k8s:test .
docker run --rm -p 18080:8080 hello-k8s:test
```

保持容器窗口打开，另开 PowerShell：

```powershell
Invoke-RestMethod http://localhost:18080/
Invoke-RestMethod http://localhost:18080/healthz
```

首页 `message` 应为新内容，`version` 在本地是 `local`；健康接口应返回 `ok`。验证完回容器窗口按 `Ctrl+C`。若 `docker build` 在拉取 `python:3.12-slim` 时失败，先检查 Docker Hub 网络或 Docker Desktop 代理设置，构建未成功前不要继续发布。

### 第 3 步：提交并推送

```powershell
git add app.py
git diff --cached
git commit -m "feat: release version 2"
git push origin main
```

`git diff --cached` 应只包含本次要发布的改动。推送被拒绝时重新 `git fetch origin main` 检查远端变化，不要强制推送。

### 第 4 步：看流水线

打开 [GitHub Actions](https://github.com/zsong0348-pixel/hello-k8s-cicd/actions)，进入最新的 `ci-cd` 运行，等待绿色 `Success`。流水线依次测试 `/healthz`、构建镜像、推送 GHCR、更新并提交 `k8s/deployment.yaml`。失败时打开红色步骤读日志，先修正原因。流水线成功后，GitHub 仓库应多出一条 `chore: deploy ... [skip ci]` 提交；这条提交不会再次构建镜像。

### 第 5 步：等 Argo CD 和 Kubernetes

```powershell
kubectl -n argocd get application hello-k8s
kubectl -n hello rollout status deployment/hello-k8s --timeout=5m
kubectl -n hello get pods
```

Argo CD 自动检查 Git，通常无需点 `Sync`。等待它变为 `Synced / Healthy`，Deployment 成功滚动更新，两个 Pod 都 `1/1 Running`。`Progressing` 表示尚在更新；超过数分钟仍不恢复时按第 8 节排查。若想在界面看是哪一步，按 [Argo CD 使用文档](03-ArgoCD使用文档.md) 第 4 节登录查看。

### 第 6 步：确认用户看到新版本

保留或重新启动第 4 节的端口转发，刷新 `http://localhost:8081/`。`message` 应为 `hello from version 2`，`version` 应是刚发布的 Git SHA。旧页面未变化时，先确认 Actions 的部署提交与当前 Deployment 镜像：

```powershell
kubectl -n hello get deployment hello-k8s -o jsonpath="{.spec.template.spec.containers[0].image}"
```

## 6. 查看状态和日志

```powershell
kubectl -n hello get pods -o wide
kubectl -n hello describe deployment hello-k8s
kubectl -n hello get events --sort-by=.lastTimestamp
```

先获取一个真实 Pod 名，再运行：

```powershell
$podName = kubectl -n hello get pods -l app=hello-k8s -o jsonpath="{.items[0].metadata.name}"
kubectl -n hello logs $podName
kubectl -n hello describe pod $podName
```

没有 Pod 时，先检查第 3 节的 Deployment 和 Events。持续看日志用 `kubectl -n hello logs -f $podName`，按 `Ctrl+C` 退出。

## 7. 回滚

本项目自动同步 Git，正式回滚要通过 Git 提交。先确认要撤销的是哪次代码提交，不要直接照抄示例 SHA：

```powershell
git fetch origin main
git log --oneline -10 origin/main
```

工作区干净且本地分支已跟上远端时，撤销错误代码提交。把第二行引号内替换成上一步找到的真实 SHA：

```powershell
git pull --ff-only origin main
$badCommit = "填入错误代码提交SHA"
git revert $badCommit
git push origin main
```

这次推送会重新触发 Actions，构建一张新镜像，再由 Argo CD 部署。等待第 5 节的 Actions、Argo 和页面验证全部完成。`git revert` 撤销的是代码改动；Actions 仍会生成一个新的部署提交。若需快速恢复旧镜像，应由维护者修改 `k8s/deployment.yaml` 中的镜像和 `APP_VERSION` 为同一个已存在的旧 SHA，提交并推送，再验证 Argo 同步。不要把 `kubectl rollout undo` 当作持久回滚：本项目启用了 `selfHeal`，Argo CD 会把手工回滚的集群恢复到 Git 声明的版本。

## 8. 常见问题

| 现象 | 先做什么 |
|---|---|
| `kubectl` 连不上集群 | 打开 Docker Desktop，检查 Kubernetes 已启用，执行 `kubectl config current-context` 和 `kubectl get nodes`。 |
| `localhost:8081` 连不上 | 确认 `port-forward` 窗口仍运行；8081 被占用时按第 4 节改用 18081。 |
| `ImagePullBackOff` | 按第 6 节获取 `$podName` 后运行 `kubectl -n hello describe pod $podName` 看 Events，检查 GHCR Package 是否 Public 及镜像地址。 |
| Application `OutOfSync` | 按 Argo 文档第 5 节检查仓库连接、同步错误和 `k8s/` 路径；刚推送时先等待自动同步。 |
| Application `Progressing` | 先看 `kubectl -n hello rollout status deployment/hello-k8s --timeout=5m`；超时后检查 Pod 的 `describe` 和 Events。 |
| Actions 失败 | 打开最新运行的红色步骤；常见原因是测试、GHCR 推送或自动提交 `main` 的权限。 |
| `git pull --ff-only` 失败 | 看 `git status -sb` 和 `git log --oneline --left-right main...origin/main`；不要直接强推。 |

## 9. 操作原则

- 不要提交密码、Token、私钥或生产密钥。
- 正常发布通过 Git；不要直接 `kubectl edit deployment` 或手工改集群。
- 不要随意删除 `argocd`、`hello` 命名空间。
- 部署镜像用 Git SHA，不依赖 `latest` 判断版本。
